## Method notes (affect reading of the evidence)

- One `logread -f` capture per device per step, restarted every step. Capture windows
  overlapped (background collectors ran ~200–280 s), so step evidence below was isolated
  strictly by timestamp; adjacent steps' data appears in the same files.
- Touch-side `logread -f` sessions yielded no history and nothing new while the Touch
  slept, so no live Touch evidence existed during the session. The gap was closed the
  next morning: while tethered (locked screen, after dropbear came up), a one-shot
  `logread` dumped the full 2824-line ring buffer (covers 23:29:59–14:03 Touch-local
  time), plus SyncCounter (unchanged: syncCount 0). Raw:
  `/tmp/melodious-research/private/g1-g4/touch-logread-full.log` (private, not in repo).
  G1a (pressed 23:29:13) predates the buffer start and stays hub-only.
- Touch clock vs hub clock: the hub clock is rock-steady (10.01 s poll cadence all
  night); the Touch clock runs ahead by a wobbling offset (+0.14 s at 23:33, +2.1 s at
  09:00, +4.0 s at 09:12) that jumps across suspend/resume cycles. Cross-device timing
  below is correlated by event SEQUENCE, not absolute subtraction; intra-device
  intervals are exact.
- The Touch hal `hot.1.*` lines log verb + id only — payload fields (`indexInMenu`,
  `deviceId`) appear nowhere at default level on either device.
- Hub `logread -f` streams new entries only; step windows are complete.
- My own SSH logins appear in the hub log as dropbear authpriv lines (read-only noise).

## G3 — long-press key, timed holds (CONFIRMED with timing caveat)

- Key: `<cmdRW>` hard key in `<activityA>`; short = `<cmdRW>`, long = `<cmdPrevTrack>`
  (from that activity map; no long action on most other keys).
- First 0.4 s attempt: owner actually held ~800 ms (press req 13:02:13.537, release req
  13:02:14.334); two `hold`s; long fired once (`<cmdPrevTrack>`, modifier `fire`,
  13:02:14.198) plus a `control.button?pressType` broadcast. Treated as an accidental
  long data point, then the short hold was redone properly.
- Redone short (~143 ms, press req 13:02:54.159, release req 13:02:54.302, zero holds):
  at release the hub ran `<cmdRW>` (modifier `fire`) plus a `pressType` broadcast.
  Short-at-release: CONFIRMED.
- ~0.7 s attempt: actual ~1.44 s (press req 13:03:35.442, release req 13:03:36.880; four
  holds). Long fired once after the 2nd hold (`<cmdPrevTrack>` fire at 13:03:36.083,
  +607 ms after press) plus `pressType`; later holds were heartbeats only; release
  executed nothing (no `he.m.device` line). Long-once: CONFIRMED.
- ~1.5 s attempt: actual ~2.04 s (press req 13:04:35.959, release req 13:04:37.998; six
  holds). Long fired once after the 2nd hold (+609 ms), plus `pressType`; release
  executed nothing. Long-once: CONFIRMED.
- Threshold: in all three long cases the long action fired on the 2nd hold, ~607–640 ms
  after the press dequeued (Touch 300 ms cadence: holds at ~+300/+610 ms). Effective
  threshold ≈ 600 ms (2nd hold), consistent with the ~550 ms hub rule. Owner finger
  timing overshot every target, but outcomes bracket the threshold: ~143 ms → short,
  ~800 ms → long.
- `pressType` broadcasts (websocket `broadcast … cmd: control.button?pressType`,
  58 bytes for long, 59 for short) were emitted ONLY for this long-armed button
  (present in all four G3 presses, absent in G1a/b/c, G2, G4, G1d windows).
- Touch side: hard `keyPress` → `hot.1.control.button?press` within ~25 ms; holds at
  Touch ~300 ms cadence (G3b: press + holds at +296/+606/+950 ms…); short redo:
  `keyPress` → press, `keyRelease` 151 ms later → release, zero holds. This nails the
  Touch-side cadence behind the ~600 ms effective threshold (2nd hold).
- Whether the Touch UI receives/acts on `pressType`: the Touch log contains ZERO
  notify-receipt lines of any kind (only `luadraws registration for notify successful`
  at boot) — receipt is unproven and unlogged at default level.

## Surprises

1. `<deviceSTB>` (streaming box) executes entirely over BT HID keyboard reports
   (`kbdhidmanager`, transport 32) — hard keys, soft buttons, and digits alike — not IR.
2. `pressType` broadcasts are emitted only for the long-press-armed button, with
   different sizes for short (59 B) vs long (58 B).
3. Touch-side logging was recovered after the session (one-shot `logread` while
   tethered; see Method notes). It upgraded nearly every Touch prediction to direct
   evidence — except `pressType`/notify receipt, of which the Touch log shows zero
   trace (neither receipt nor action), and G1a, which predates the recovered buffer.
4. An empty-name `<deviceAMP>` `fire` line appears in the `<activityB>` EnterAction
   sequence (`command: ` empty). Cosmetic log oddity; action executed with transport 1.
5. The Touch wakes itself hourly (resume + `{errorCode=200,count=0}` poll + suspend,
   at :35 past, all night) — maintenance wakes independent of any user action.
6. Touch and hub clocks disagree by seconds and the offset jumps across suspend/resume
   cycles (hub steady at 10.01 s cadence); correlate cross-device events by sequence,
   not absolute timestamps.

## Addendum (2026-10-26): tethered-state logging limitation

Owner request: pull live Touch logs while tethered, and document what tethering does.
Method stayed read-only (SSH `logread -f` attempts, local Mac USB/ping checks only).

Findings:
- While plugged into the Mac over USB, the Touch sits on the myharmony.com locked
  screen (stable, not cycling). It cannot be used as a remote in this state, so no
  button traffic exists to log.
- USB presents an RNDIS/Ethernet gadget, but with a DIFFERENT gadget MAC address than
  the previous session's enumeration. macOS therefore treated it as a new interface and
  assigned a link-local address instead of the expected static 192.168.2.2/24, leaving
  192.168.2.1 unroutable. The owner restored it with
  `sudo ifconfig en10 inet 192.168.2.2 netmask 255.255.255.0` (Mac-side, reversible).
- After the route was restored: USB link up, ICMP to 192.168.2.1 answered (<1 ms), but
  port 22 stayed closed across 16+ consecutive attempts spanning several minutes with
  the locked screen stable throughout (dropbear comes up late after plug-in/boot).
- ~10 min after plug-in, SSH succeeded and a one-shot `logread` retrieved the full
  2824-line buffer plus SyncCounter (unchanged). So tethered log access works, but only
  after the Touch finishes settling, and the locked screen means no live button traffic
  exists to watch — tethered logs are retrospective (ring buffer), never live presses.
- Practical notes: the gadget MAC changes per enumeration (Mac binding breaks each
  time); `logread -f` over this link streams live lines only (no history dump) and
  stays silent while the Touch sleeps. Raw retry log:
  `/tmp/melodious-research/private/g1-g4/touch-monitor.log` (private, not in repo).
